# 后台设置流程审计

## 1. 当前后台设置版图

后台共有 55 个导航路径、14 个一级分组。配置入口不是一个独立模块，而是按业务域分散：

| 配置域 | 当前入口 | 主要任务 |
| --- | --- | --- |
| 用户与合规 | KYC 审核、安全策略、国家配置 | KYC 准入、登录与支付验证、国家目录 |
| 钱包与渠道 | 资产、充值网络、地址池、快速充值 | 资产开关、链网络、地址资源、GMPay 渠道 |
| 行情与交易 | 交易对、行情策略、行情订阅 | 交易目录、模拟行情、第三方行情运行态 |
| 产品配置 | 贷款、竞猜、闪兑、秒合约、杠杆、理财 | 产品条款、费率、限额、状态与结算规则 |
| 平台集成 | 品牌、SMTP、上传 | 品牌展示、邮件通道、对象存储 |
| 风控 | 风控规则 | 业务动作阻断规则 |
| 运营动作 | KYC、提现、贷款订单、新币生命周期 | 审核、结算、派发与人工处置 |
| 审计 | 审计日志 | 查询管理员操作留痕 |

## 2. 当前存在的四类流程

### A. 通用资源 CRUD

`资源列表 -> 添加/修改 SideSheet -> ConfirmAction 填写原因 -> POST/PATCH -> 刷新列表 -> 状态切换`

适用于资产、国家、交易对、充值网络、贷款/秒合约/杠杆/理财产品等。优点是列表和操作一致；缺点是每个业务仍手写表单状态与校验，且提交即生效。

### B. 单例全局配置

`GET 当前配置 -> 本地编辑全部字段 -> 确认原因 -> PATCH 整体覆盖 -> 回读`

适用于安全策略、平台品牌、上传、快速充值、竞猜设置。多数页面没有版本、草稿、差异对比、并发保护或回滚。

### C. 配置与运行态分离

行情订阅已经实现：

`保存配置版本 -> 标记 needs_reload -> 人工重载 -> 显示 applied_version/运行结果`

行情策略进一步实现：

`编辑 -> 无副作用预览 -> 创建不可变新版本 -> 激活 -> 查看版本历史 -> 复制旧版本为新版本回滚`

这两类流程是后续统一配置中心的主要参考。

### D. 审核/人工处置

`待处理队列 -> 查看详情与上下文 -> 填写审核原因 -> 批准/拒绝/冲正/结算 -> 留痕`

适用于 KYC、提现、贷款订单等。这类任务不应继续与全局配置编辑混在同一页面层级。

## 3. 已确认的关键问题

### P0-1：角色表存在，但后台没有真正 RBAC

- 数据库有 `admin_roles.permissions`。
- 管理员访问令牌只有 `Admin` scope，不含角色或权限声明。
- Rust 管理接口只检查 `AdminAuth`，没有资源/动作级权限判断。
- React 导航对所有管理员展示全部 55 个入口。

结果是“客服、财务、风控、超级管理员”无法做最小权限隔离。建议建立稳定权限码，例如 `wallet.withdraw.review`、`market.feed.publish`、`risk.rule.write`，后端逐路由强制校验，前端仅用于隐藏无权限入口，不能把前端隐藏当授权。

### P0-2：高风险配置普遍是立即覆盖，缺少发布模型

除行情订阅和行情策略外，大多数配置保存后立即生效。推荐统一目标流程：

`编辑草稿 -> 服务端校验 -> 联通/业务预检 -> 查看差异与影响 -> 提交发布 -> 审批（高风险） -> 生效/运行态确认 -> 可回滚`

资金、费率、风控、登录安全、渠道密钥等配置至少需要版本快照；高风险变更应支持双人复核。

### P0-3：审计覆盖不完整且部分“原因”被静默丢弃

- 预测设置和下注资产写入不要求原因，也不写统一 `admin_audit_logs`。
- 贷款产品前端发送 `reason`，但后端 DTO 和用例不消费，创建/修改/状态变更没有统一审计。
- 审计响应有 `ip`，统一写入对象和 SQL 却未写 IP，后台 IP 列缺少真实数据。
- 当前日志页面只显示动作、对象和原因；`before_json/after_json` 主要依赖原始数据查看，没有字段级中文差异。

应统一所有配置写请求的 actor、reason、request/correlation ID、来源 IP、before/after、配置版本和审批信息，并在后台提供可读差异与对象跳转。

### P0-4：没有乐观并发控制

- 所有设置页均没有 `beforeunload`/路由离开拦截。
- 多数保存请求没有 `version`、ETag 或 `If-Match`。
- 预测设置后端已明确说明：写入后回读可能读到另一管理员刚保存的值。

需要同时增加：前端脏数据保护、服务端 revision、冲突返回 `409`、冲突差异比较与重新加载/合并入口。

### P0-5：高风险配置没有统一双人复核

提现本身有审核，但“提现开关/费率、风控规则、安全策略、行情源、秒合约/杠杆参数”等配置变更仍可由单个管理员直接生效。建议按权限和风险等级配置 `maker-checker`，禁止创建人与审批人为同一人。

## 4. P1 业务流程优化

### P1-1：建立配置中心总览

当前 55 个入口分散且没有搜索。建议新增“配置中心”总览，但保留业务域入口：

- 全局搜索配置项和页面。
- 显示当前状态：正常、未配置、待测试、待发布、待重载、发布失败。
- 显示负责人、最后修改、已应用版本和最近测试时间。
- 提供“我的待审批”“最近变更”“存在风险的配置”。

### P1-2：区分配置态、发布态和运行态

行情订阅已有 `version/applied_version/needs_reload`，其他外部集成也应采用相同语义：

- SMTP：已保存、已启用、最近测试成功、最近发送错误。
- 上传：已保存、凭据可用、最近测试上传、公开访问校验。
- GMPay：已保存、联通测试、回调校验、最近成功订单。
- 安全策略/产品配置：已发布版本、有效时间、当前运行版本。

### P1-3：统一依赖预检与影响分析

启用配置前由后端返回结构化 preflight：

- 交易对依赖基础/计价资产启用、精度和行情来源。
- 闪兑、秒合约、杠杆、贷款、理财依赖资产、钱包账户、费率和状态。
- SMTP/上传/快速充值依赖凭据、网络、回调地址和连通性。
- 停用资产或网络前列出引用产品、现有余额、在途订单和地址占用。

前端确认框应展示影响对象，而不只是要求填写原因。

### P1-4：拆分配置任务与运营任务

- 将 KYC“规则配置”和“KYC 审核队列”拆成两个路由，互相提供快捷链接。
- 将竞猜“全局设置/下注资产”和“同步运行/日志”拆成配置与运行两个工作区。
- 将当前管理员两步验证移到右上角“账号安全”，不再放在全局系统配置。
- 新币生命周期动作应从具体项目详情进入，而不是独立页面手填项目 ID。

### P1-5：统一引用字段选择

继续把裸 ID 输入替换为搜索选择器和上下文详情。优先处理：

- 新币项目、申购、用户、费用资产。
- 用户分配代理。
- 风控规则对象。
- 遗留理财产品动作页面。

选择后同时展示名称、状态、ID 和关键约束，服务端仍按 ID 提交。

### P1-6：把后端已有状态展示出来

后台 Dashboard 后端已经返回 24 小时管理员操作数和最近操作，前端没有消费。应增加：

- 最近配置变更。
- 待发布/待重载配置。
- 外部通道健康度。
- 失败任务和审计异常。

环境标签当前固定显示“生产环境”，应改为后端/构建元数据驱动，避免测试环境被误认为生产环境。

### P1-7：收敛 SMTP 双写入口

`/smtp/config` 默认单例与 `/smtp/configs` 具名配置同时可写。建议迁移所有调用到具名配置，旧入口进入弃用期并最终只读或移除，避免默认配置和发信策略发生漂移。

## 5. P2 工程与体验优化

- 建立统一 `AdminSettingsPage`/`ConfigEditor` 壳：加载、错误、脏状态、差异、确认、提交、刷新、审计链接。
- 管理后台真正使用 React Query 管理读取、缓存失效和 mutation；当前仅登录使用 mutation，大多数设置页重复手写 `useEffect/useState/load/submitAction`。
- 使用共享 schema 生成前端校验与服务端错误映射，统一金额精度、百分比、秒/天等单位。
- 把 SMTP（841 行）、行情策略（829 行）、竞猜配置（619 行）拆成领域组件和 hooks，减少表单逻辑耦合。
- 清理未挂路由的 `ProductStatusActions` 和仅作包装的重复页面，避免出现多个配置入口。
- 审计日志增加中文动作映射、字段级差异、对象详情链接、导出和时间范围筛选。
- 对敏感密钥增加“最后轮换时间、最后验证时间、即将过期、测试结果”，不回显明文。

## 6. 推荐实施顺序

### 第一阶段：治理底座（P0）

1. 实现后台 RBAC 与权限码。
2. 新增统一配置 revision、差异、审计上下文和 `409` 并发冲突合同。
3. 修复预测配置与贷款产品审计，补齐来源 IP。
4. 建立高风险变更审批模型。

### 第二阶段：迁移高风险设置

优先顺序：

1. 安全策略。
2. 预测设置与下注资产。
3. 贷款产品。
4. 快速充值、SMTP、上传。
5. 风控规则、秒合约、杠杆、理财和闪兑。

每个页面迁移到统一的“校验 -> 差异 -> 发布 -> 生效状态 -> 回滚”闭环。

### 第三阶段：重组后台信息架构

1. 增加配置中心总览与搜索。
2. 拆分配置和运营路由。
3. 移动个人两步验证入口。
4. 清理重复/孤立页面和裸 ID 操作页。

### 第四阶段：运行可观测性

1. Dashboard 接入已有审计摘要。
2. 聚合外部通道测试结果和运行健康度。
3. 增加待发布、待重载、发布失败和配置漂移告警。

## 7. 建议的下一项开发任务

先做“后台配置治理底座 + 首批预测/贷款修复”，不要先大改导航视觉。该任务应包括：

1. 权限码和后端授权中间件的最小骨架。
2. 通用配置 revision/审计上下文接口。
3. 预测设置、下注资产与贷款产品接入必填原因、before/after 审计和并发保护。
4. 后台审计日志显示字段级中文差异。

完成后再迁移其他页面，避免为每个设置页重复实现一套发布和审计逻辑。
