# 后台设置流程 P0/P1/P2 全量优化

## Goal

在已完成的审计基础上，完整实施 P0 治理底座、P1 业务流程和 P2 工程体验优化，使后台设置具备最小权限、完整审计、并发保护、发布回滚、运行可观测和一致交互。

## What I already know

- 后台导航目前包含 55 个路径、14 个一级分组，其中 43 个页面使用通用 `resourceConfigs` 资源页，另有 13 个路由级独立页面。
- 设置入口分散在用户与代理、钱包资产、竞猜、行情市场、闪兑、秒合约、杠杆、理财、风控与系统配置中。
- 通用资源页已经具备列表、筛选、详情、SideSheet 表单、确认原因和刷新机制，但不同业务仍各自维护表单状态、校验和保存逻辑。
- 行情订阅已经区分“已保存版本”和“已应用版本”；行情策略已经具备不可变版本、预览和复制旧版本回滚，是当前最完整的配置流程参考。
- 绝大多数其他配置仍是“读取当前值 -> 修改 -> 立即覆盖保存”，没有草稿、差异确认、并发版本或回滚。

## Confirmed Findings

- `admin_roles.permissions` 已存在于数据库，但管理员令牌只携带 `Admin` scope，后台路由和前端导航均未按角色权限授权。
- 预测配置整体覆盖保存时不解析具体管理员、不要求原因、不写统一审计，且后端注释明确并发保存后可能回读到他人配置。
- 贷款产品前端提交 `reason`，但后端创建、更新和状态请求 DTO/用例不消费该字段，也不写统一后台审计。
- 通用审计表和响应包含 `ip`，但当前统一写入结构和 INSERT 未接收/写入请求 IP；后台“IP”列因此缺少可靠数据来源。
- 后台所有设置页均没有未保存变更拦截；除行情订阅/行情策略外也没有配置版本或乐观并发控制。
- 仪表盘后端已经返回 `audit.admin_actions_24h` 和最近操作，但后台 Dashboard 类型与页面未消费这部分数据。
- “两步验证”是当前管理员个人账号设置，却被放在全局“系统配置”分组。
- 竞猜配置页面混合全局配置、下注资产、同步执行和同步日志；KYC 页面混合全局准入规则和审核队列，配置任务与运营任务边界不够清晰。
- SMTP 同时保留默认单例 `/smtp/config` 和具名多配置 `/smtp/configs` 两套写入口，存在长期双入口漂移风险。
- 仍有新币生命周期、代理分配、风控对象等操作要求管理员手填项目/用户/资产 ID，缺少可搜索目录和上下文校验。

## Requirements

- 输出当前后台设置入口和流程类型矩阵。
- 对权限、审计、配置生命周期、运行态、依赖校验、信息架构和表单一致性分别给出问题与目标状态。
- 优化项必须按 P0/P1/P2 分级，并说明推荐实施顺序。
- 明确哪些现有流程可以作为统一模板，哪些页面应优先迁移。
- 按 P0/P1/P2 三个可独立验收的子任务实施 Rust API、MySQL 迁移、React 后台和自动化测试。
- 每个配置写入都必须形成“授权 -> 校验 -> 差异/影响 -> 确认 -> 发布 -> 运行态 -> 审计/回滚”中它所需的完整闭环。
- 保留现有对外路由和 JSON 兼容性；兼容入口收敛必须有明确弃用过渡。

## Acceptance Criteria

- [x] 已覆盖后台导航、资源配置、独立设置页和主要后端写入路径。
- [x] 已确认至少权限、审计、并发覆盖、发布回滚和页面边界五类具体缺口。
- [x] 已形成可执行的 P0/P1/P2 优化清单。
- [x] 已给出推荐的阶段性实施顺序和首批改造页面。
- [x] 审计结论写入 `research/admin-settings-workflow-audit.md`。
- [x] P0：后端强制权限码，前端按权限展示；审计补齐 actor/reason/IP/request ID/before/after/revision；高风险配置具备并发冲突和审批保护。
- [x] P1：配置中心可搜索且展示配置/发布/运行状态；配置与运营路由拆分；裸 ID 主要入口改为可搜索引用选择器。
- [x] P2：设置页共用数据/脏状态/确认壳；审计字段级中文差异；重复与孤立实现清理；核心页面自动化验证通过。

## Out of Scope

- 不改动手机端、PC 用户端的业务 UI。
- 不借此任务改变交易、钱包、结算和清算的金额规则。
- 不直接删除生产环境仍可能有调用方的兼容接口。

## Decision

用户已确认 P0/P1/P2 全部进入实施。执行顺序保持“先治理底座，再迁移高风险流程，然后重组信息架构，最后工程化收敛”；子任务按此依赖顺序验收。
