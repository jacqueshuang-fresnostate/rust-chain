# 业务闭环完善度审查

日期：2026-09-18。基线：`4bb0baf`，开始审查时工作区干净。

## 总体判断

本轮重点不是增加产品种类，而是让异常订单可处理、重复操作不重复记账、封禁可靠生效，以及让平台能够解释每笔收入和支出。

以下 P1 表示建议优先处理的业务风险，不表示已在生产发生。结论来自当前源码静态核验，未连接生产服务、未查看实际订单量、未验证部署版本。

## 已确认的缺口

### B01 / P1：秒合约人工审核缺少处理出口

- 现状：缺少事件时间行情且等待超限时，worker 将订单转为 `manual_review`，本金已在开仓时扣除。自动扫描只读取 `opened`；人工结算接口也拒绝非 `opened`；后台仅对 `opened` 启用结算按钮。
- 影响：即使随后补齐可靠行情证据，该异常单也不能经现有正常接口恢复结算；没有独立退款或异常裁决入口。
- 依据：`src/workers/seconds_contract_settlement.rs:279`、`:356`；`src/modules/seconds_contract/application.rs:435`、`:525`；`src/modules/seconds_contract/routes.rs:65`；`web/src/admin/resources/actions/secondsContract.tsx:425`。
- 建议：补异常订单工作台，支持基于可核验历史证据重新结算；无有效证据时的退款规则须先确认。记录处理人、原因、证据与终态，必要时双人复核。不能简单放开人工选择输赢。
- 验收：进入人工审核、补证或退款、用户账单、佣金处理全部闭环；重复执行只产生一次资金结果。

### B02 / P1：部分客户端重试会被当作新交易

- 现状：Mobile 理财申购、贷款申请每次调用 API 都重新生成时间戳加随机串的幂等键；PC 贷款也在调用时重新生成。理财页面失败后允许再次提交同一表单。
- 影响：首次已入库但响应丢失时，再点一次可能产生第二笔申购或借贷申请。按钮防连点不能解决响应丢失后的重试。
- 依据：`mobile/src/api/earn.ts:77`；`mobile/src/api/loan.ts:93`；`pc/src/api/loan.ts:145`；`mobile/src/views/EarnView.vue:193`。
- 建议：一次业务确认持有一个稳定请求标识；结果未知时查原单或沿用原标识重试。修改交易意图才生成新标识，并规划刷新后的恢复方式。
- 验收：模拟服务端提交成功但客户端超时，再次确认后订单数及扣款次数仍为一。
- 边界：不能概括为所有客户端都没有幂等；钱包划转已有 `RetryStableIdempotencyKeys`，可作为复用依据。

### B03 / P1：账号禁用依赖事务外会话撤销

- 现状：UserAuth、AgentAuth 校验令牌和 scope，没有管理员鉴权同等的账号状态与会话版本回查。禁用用户先提交数据库状态和刷新令牌撤销，再执行在线会话撤销。
- 影响：若提交后的会话撤销失败且旧访问会话仍有效，仅依赖这些鉴权提取器的入口没有数据库禁用状态兜底。不能把“后台已停用”直接视为所有旧会话立即失效。
- 依据：`src/modules/auth/mod.rs:626`、`:643`、`:669`；`src/modules/admin/application/users.rs:109`。
- 建议：用户与代理补账号状态、会话版本的权威校验；同步检查私有 WebSocket 和敏感资金入口；事务外撤销失败可补偿。
- 验收：故意让在线会话撤销失败，旧会话仍不得提交资金操作；恢复启用也不恢复被撤销的旧代际会话。

### B04 / P1：自动任务存在队首阻塞与重试不可运营的问题

- 现状：理财每轮取最早到期的有限批次，失败记录保留原状态；贷款每轮取最早到期的 disbursed/overdue，余额不足仍保留 overdue；佣金同样固定从最早 pending 开始扫描。
- 影响：旧异常记录填满扫描窗口后，后面的正常订单长期无法进入候选。贷款在默认批量下，前 1,000 笔长期余额不足即可阻挡后续到期单；理财默认扫描窗口为 500。
- 额外问题：佣金 worker 将普通错误也加入进程内失败集合；未达到清空阈值且进程不重启时，临时失败也可能不再自动尝试。失败集合是在查询后过滤，不能解决扫描窗口被占满。
- 依据：`src/workers/earn_auto_redemption.rs:195`；`src/workers/loan_overdue.rs:152`；`src/workers/agent_commission_settlement.rs:75`、`:143`。
- 建议：持久化下次重试时间、错误分类与尝试次数；采用公平扫描或游标；增加异常队列、重试入口、处理时限和告警。区分贷款“等待余额”与系统执行失败。
- 验收：构造超过窗口上限的失败或等待记录，尾部正常单仍能被处理；临时故障恢复后无需重启服务即可恢复。

### B05 / P1：平台账务覆盖尚不完整

- 现状：充值、提现确认、理财、借贷和部分新币路径已写平台分录。现货、杠杆、闪兑、秒合约、预测及代理佣金相关路径尚未看到对应的统一平台分录写入。
- 影响：用户钱包流水可追踪，不等于能完整核对平台手续费收入、兑付支出、佣金成本与坏账。现有“幂等审计”主要检查重复键、孤儿流水和超期队列，不能替代全量金额对账。
- 依据：全仓检索 `platform_financial_journal` 的写入点；`src/modules/wallet/infrastructure/shared.rs:160`；`src/modules/earn/infrastructure.rs:704`；`src/modules/loan/infrastructure.rs:1522`；`src/modules/admin/infrastructure/financial_idempotency.rs:128`。
- 建议：按业务定义平台科目和资金性质，补齐分录；按资产分别核对用户负债、托管资产、做市库存、收入、费用和坏账，避免跨币种直接求和；增加日终差异与处理记录。
- 验收：每笔交易和退款可穿透到相关订单及账务记录；历史数据明确覆盖起点和补录策略，不制造历史资金。

### B06 / P1：人工现货成交缺少操作者审计与后台工作流

- 现状：`/spot/fills` 能结算真实双边资金，但路由丢弃管理员 claims，调用链不传管理员 ID 与原因；后台资源只提供订单和成交列表，未发现 fills 提交界面。
- 影响：运营不能在标准后台完整处理这类成交；通过接口操作后，也缺少本业务事务内“谁因何原因促成成交”的审计证据。
- 依据：`src/modules/spot/routes.rs:207`；`src/modules/spot/application/settlement.rs:217`；`web/src/admin/resources/resourceConfigs.tsx:977`；`web/src/admin/routes.tsx:116`；全仓 Web 检索 `/spot/fills` 仅命中权限映射。
- 建议：先确定是否保留人工成交能力；若保留，补成交预览、对手订单核验、稳定幂等标识、原因和同事务审计，再接后台入口。
- 验收：每笔人工成交能查处理人、双方订单、价格数量、原因及资金结果；重复提交不重复成交。
- 历史纠正：当前代码已有现货行情触发成交，并接入市场摄取及下单流程，不能继续认定“没有自动撮合”。成交依赖真实预充值做市库存，库存不足会拒绝成交。依据：`src/modules/spot/application/order_creation.rs:75`、`src/modules/market/infrastructure/adapters/ingestion.rs:490`、`src/modules/spot/infrastructure/wallet_accounts.rs:272`。

## 需确认的业务规则

### B07 / P2：借贷需要明确用户总授信与资金池上限

- 现状：申请检查单笔 min/max、KYC、抵押率；审批检查订单状态与抵押风险。本轮检查的申请/审批路径未见按用户汇总未结清债务、待审额度预占或产品资金池总额度。
- 风险：单笔额度不等于累计授信。多笔申请即使都符合单笔要求，人工逐笔批准后仍可能产生超出业务预期的累计敞口。
- 依据：`src/modules/loan/application.rs:295`、`:330`、`:850`、`:910`。
- 待确认：信用贷每人总额度、待审是否占额、有逾期能否再借、产品总放款上限，以及部分还款/展期是否允许。抵押贷已有健康扫描和清算，不能说借贷完全没有回收机制。
- 验收方向：总额度及预占在同一事务按确定口径更新；并发申请/审批不超额；取消、拒绝和还款正确释放对应额度。

### B08 / P2：代理佣金的计佣口径需要明确

- 现状：秒合约按押注金额生成 pending 佣金，打款检查订单是否 settled，没有按输赢结果筛选。
- 依据：`src/modules/seconds_contract/application.rs:458`；`src/modules/admin/service/agents.rs:29`。
- 判断：若约定“按成交量返佣”，输单返佣可以是正确行为；若约定“按平台净收入或有效费用返佣”，则需要不同基数。不能仅凭输单返佣就认定财务漏洞。
- 待确认：计佣基数、退款/无效单规则、人工裁决、已付佣金冲回与负余额处理、计佣规则版本快照。
- 验收方向：每笔佣金展示来源、基数、费率、规则版本和最终支付/冲回记录。
