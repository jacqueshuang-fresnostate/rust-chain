# Research: production mobile product/account secondary workflow gaps

- Query: Compare production mobile product/account secondary workflows with `mobile/sites-prototype/app/page.tsx`; cover swap, product hub, earn, loan, new coins list/detail/records, prediction, seconds contracts, profile settings, KYC, security, bindings, referrals, language, and relevant login/auth. Recommend prototype pages, meaningful controls, and acceptance checks.
- Scope: internal
- Date: 2026-07-26

## Findings

### Executive summary

The production mobile client already has a complete secondary-page route tree. The prototype has only six top-level in-memory views (`home`, `markets`, `spot`, `contract`, `assets`, `profile`) and represents every product entry with one generic informational sheet whose CTA only closes the sheet and shows a toast (`mobile/sites-prototype/app/page.tsx:54`, `mobile/sites-prototype/app/page.tsx:1151`, `mobile/sites-prototype/app/page.tsx:1194`, `mobile/sites-prototype/app/page.tsx:1267`). Account rows similarly show toasts; profile identity, verification, and metrics are hard-coded, the settings icon has no handler, and logout is simulated (`mobile/sites-prototype/app/page.tsx:1093`, `mobile/sites-prototype/app/page.tsx:1101`, `mobile/sites-prototype/app/page.tsx:1107`, `mobile/sites-prototype/app/page.tsx:1127`, `mobile/sites-prototype/app/page.tsx:1143`).

The prototype should replace the generic product sheet and account toasts with state-backed logical routes. These do not need Next.js filesystem routes: a typed `activeRoute` plus a small internal history stack is sufficient. Keep the six bottom tabs as the root shell, hide the bottom bar on secondary/auth pages, and provide safe Back fallbacks matching production. Production route depth and fallbacks are defined in `mobile/src/router/index.ts:47-74`; production navigation contracts require push for drill-down pages, replace for main tabs/auth completion, and fallback Back for direct-open pages (`.trellis/spec/mobile/navigation-and-localization.md:25-46`).

### Cross-cutting prototype implementation recommendations

1. **Route model:** introduce logical route strings matching the matrices, plus `pushRoute`, `replaceRoute`, and `goBackOr(fallback)`. Root-tab changes replace the current root; secondary pages push; successful login/register replace; every secondary page has a deterministic fallback. This mirrors production’s depth/fallback table (`mobile/src/router/index.ts:41-77`) without requiring separate Next route files.
2. **Shell behavior:** hide the six-item bottom navigation for every secondary/auth route. Keep the global header only where it helps; secondary pages should use a compact page header with Back and optional action. Direct-open simulation must never leave a blank screen.
3. **Auth model:** use an explicit local demo session (`guest`/`member`) and a sanitized pending route. Protected pages show the reusable LoginRequired state and “立即登录”; production uses the current full path as redirect (`mobile/src/components/LoginRequiredState.vue:9-23`). Auth expiry in production clears the session and replaces Login with the current route as redirect (`mobile/src/App.vue:13-21`).
4. **Interaction depth:** every P0 page needs at least one input-dependent state transition, not merely navigation plus toast. Use deterministic mock data and local state; do not call production APIs or mutate real accounts.
5. **Financial tickets:** present validation before submit; quote-based products (Swap and Prediction) must have separate Quote and Confirm states with expiry; submit buttons must disable during the simulated action; successful actions add/update exactly one record.
6. **Status coverage:** include loading, empty, error, success, unauthenticated, insufficient-balance, and duplicate-submit prevention where applicable. Unknown backend-like status strings should remain visible rather than receive a misleading translation.
7. **Accessibility/layout:** dialogs use `role="dialog"` and `aria-modal`; tabs/radio groups expose selected state; all secondary pages and sheets remain usable at 390×844, have no horizontal overflow, keep bottom CTAs above safe-area insets, and allow long content/dialogs to scroll.
8. **Testing:** extend the current source/SSR contract tests, which currently cover only the root shell, icon/motion/mobile-nav rules, Web3 absence, wallet actions, and split Spot/Contract columns (`mobile/sites-prototype/tests/rendered-html.test.mjs:26-121`). Add static contracts for every logical route and automated interaction/browser checks for the P0 acceptance checks above.

### Suggested delivery slices

1. **Navigation/auth foundation:** logical route stack, secondary header, auth state, LoginRequired, Login, Language.
2. **Product P0:** Product Hub, Swap, Earn, Loan, New Coins list/detail/records, Prediction, Seconds.
3. **Account P0:** dynamic Profile, KYC, Security, Bindings, logout.
4. **Account/auth P1:** Referrals, 2FA, Register, Forgot Password.
5. **Regression/accessibility:** 390×844 checks, direct-open Back fallbacks, no toast-only product/account rows, reduced motion, keyboard/focus, tests.

### Code patterns

- Route depth and `backFallback` are explicit for all requested secondary pages (`mobile/src/router/index.ts:47-74`).
- Main-tab history replacement, drill-down push, safe fallback Back, auth redirect sanitization, and full locale switching are project contracts (`.trellis/spec/mobile/navigation-and-localization.md:25-58`).
- Protected views generally retain public discovery where meaningful (Loan, New Coins, Prediction) and gate write/history surfaces with `LoginRequiredState`; Earn and Seconds gate the whole workflow (`mobile/src/views/LoanView.vue:41-53`, `mobile/src/views/NewCoinsView.vue:22-34`, `mobile/src/views/PredictionView.vue:38-49`, `mobile/src/views/EarnView.vue:35-40`, `mobile/src/views/SecondsView.vue:34-39`).
- Financial writes carry backend/user-owned quote or generated idempotency keys; the prototype should mimic the two-step semantics but must remain local-only (`mobile/src/api/swap.ts:67-85`, `mobile/src/api/earn.ts:51-60`, `mobile/src/api/loan.ts:75-90`, `mobile/src/api/prediction.ts:76-101`, `mobile/src/api/seconds.ts:75-82`).
- Production token handling injects Bearer auth, retries once after 401 through refresh, and emits auth expiry when refresh fails (`mobile/src/api/client.ts:47-99`).
- Current prototype product/account actions converge on `setActiveProduct`/toast rather than separate routes (`mobile/sites-prototype/app/page.tsx:1277-1278`, `mobile/sites-prototype/app/page.tsx:1304-1331`).

## Caveats / Not Found

- `task.py current --source` returned no session-scoped active task. The user supplied the exact task directory and output path, so this research was persisted there without changing task metadata.
- This was source-level research only. No deployed mobile binary, live backend, or production account was opened, and no real financial/auth/KYC action was performed.
- The CodeGraph index exposed only part of `mobile/src`; findings were verified against line-numbered source instead.
- The production mobile Prediction page currently has one list/ticket route, although the backend spec also describes a market-detail API and a PC list/detail contract. A separate mobile Prediction detail page is optional future scope, not required to match the current production mobile route.
- The backend Earn spec includes product-level redemption fees, but the current mobile `EarnProduct` mapping does not expose those fee fields (`mobile/src/api/earn.ts:5-16`). The prototype should not invent precise fee values; use current mobile fields or a clearly illustrative rules disclosure.
- Loan products expose `minKycLevel`, but current mobile client-side `canApply` checks amount/collateral rather than the loaded user KYC level (`mobile/src/views/LoanView.vue:30-39`). Display the requirement and treat server validation as authoritative unless this task explicitly adds a demo eligibility rule.
- Production profile code calls the username editor a nickname, while the authentication spec defines username as a normalized login identifier. Prototype copy and validation should follow the spec, not imply a free-form display name (`.trellis/spec/backend/user-authentication.md:25-35`).
- Existing prototype tests do not exercise secondary routes or interactions. Browser-level acceptance will need additional tooling or tests during implementation.
