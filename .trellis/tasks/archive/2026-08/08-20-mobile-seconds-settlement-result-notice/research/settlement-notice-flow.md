# 秒合约结算提示数据流审计

## 当前链路

1. `/seconds` 首次加载 `GET /seconds-contracts/orders`，将历史订单与活动订单一起写入 `orders`。
2. 页面每秒更新倒计时；活动订单到期后进入 `queueExpiredOrderReconciliation()`。
3. `reconcilePrivateState()` 并行刷新订单和现货钱包，订单成功时调用 `applyReconciledOrders()`。
4. 后端结算是权威来源：终态订单为 `status = settled`，结果字段为 `result = win|loss`；输赢与钱包入账在服务端事务中完成。

## 现有缺口

- 对账后活动订单直接从 `activeOrders` 计算结果中消失，页面仅更新钱包和历史数据，没有显式告诉用户输赢。
- 首次加载同时包含历史订单，因此不能简单对所有 `result` 非空订单弹出提示。
- 页面支持多个并行订单，同一轮对账可能产生多个结果；单个 `success` 字符串会覆盖结果并丢单。
- 网络重试会重复返回相同终态订单，需要会话级去重。

## 选择方案

- 建立只存在于 `SecondsView` 生命周期内的追踪器。
- `reconcile(nextOrders)` 先检查此前已追踪的活动订单是否首次出现 `win|loss`，再把本次列表中的活动订单加入追踪集合。
- 首次加载时追踪集合为空，因此历史终态不会触发；活动订单会成为后续状态转换的基线。
- 开仓响应立即调用 `track(order)`，避免订单在首次服务端列表可见时已经结算而漏报。
- 已通知 ID 保留到页面卸载，保证重复轮询不重放；取消订单从追踪集合移除；暂缺结果的非活动订单继续保留，允许后续接口补齐结果。
- 返回结果按 `expiresAt`、`id` 稳定排序后进入 FIFO 队列，避免接口倒序导致展示顺序跳动。

## UI 选择

- 采用 Teleport 非模态悬浮结果卡，而不是复用下单确认模态框。
- 卡片固定在 Header 下方、限制在 448px 应用画布内，页面仍可滚动和下单。
- 盈利/亏损使用既有正负语义色和共享盈亏展示模型；不新增第二套计算公式。
- 每张卡提供关闭、继续交易和查看历史；队列超过一笔时显示剩余数量。

## 风险边界

- 客户端倒计时归零不等于结算完成，只能启动对账，不能触发输赢 UI。
- 订单接口失败时保持活动订单和重试状态，不生成结果。
- 钱包刷新失败但订单已返回权威结果时仍可提示输赢，同时保留现有刷新警告。
- 退出登录、组件卸载或私有状态清空必须同时清理追踪器和队列。
