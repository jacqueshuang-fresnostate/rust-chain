# 业务优化后复审

日期：2026-09-19，Asia/Hong_Kong。基线：`4bb0baf` 加当前未提交工作区，包含上一轮八项业务加固。此次只审查和记录，不修改业务代码、不启动数据库、不操作线上。

## 结论

下一轮应优先解决“用户确认的交易是否就是实际执行的交易”和“代理看到的账单是否能解释资金变化”，而不是继续增加产品入口。

本轮确认了五项应优先处理的客户端/业务接口缺口，以及三项后续运营完善方向。P1 是修复优先级，不代表已证明线上发生损失。上一轮的资金事务、权限、分录和策略能力已交付；这里不将它们重新描述为不存在。

## R01 / P1：PC 闪兑重新报价并直接确认，未知结果重试可能重复兑换

**现状：** 页面展示的报价由 `refreshQuote` 获取；点击兑换的 `handleSwap` 不确认该报价，而是重新请求一个报价并立即确认新 ID。失败后保留输入，用户再次点击会再生成一个新报价，不会复用上次确认的身份。

**业务影响：**

- 用户看到报价 A，实际执行的可以是报价 B，缺少新价格的再次确认。
- 若 B 已成交但响应丢失，再点会创建并确认 C。后端对同一报价的防重不能阻止两个不同报价分别成交。

**本地验证：** 用 Vue SFC/TypeScript AST 提取并执行当前 `handleSwap` 函数，替换报价/确认接口为内存模拟。第一次模拟“已成交后响应丢失”，再次执行函数得到 `new-quote-1`、`new-quote-2` 两个确认 ID；原展示 ID 为 `displayed-quote`。模拟提交次数为 2，无生产网络请求。这证明客户端存在该路径，不等于真实资金已损失。

**建议验收：** 确认当前展示且未过期的报价；过期或价格变化需重新展示并再次确认；未知结果保存原 quote ID 并查询权威订单状态，不能自动创建另一笔交易；覆盖断网、重试、刷新和账号切换。后端可保留既有重复确认 409，但客户端须能核实原交易是否成功。

**依据：** `pc/src/views/Swap.vue:173`、`pc/src/views/Swap.vue:195`、`pc/src/api/swap.ts:61`。

## R02 / P1：PC 闪兑金额经过 Number 后再提交，损失原始精度

**现状：** 输入字符串经 `Number(fromAmount.value)` 转为浮点；报价接口收到 number，再用 `String(amount)` 发给后端。余额、限额和报价展示也存在 Number 转换。后端 Decimal 无法恢复已经在客户端丢失的数字。

**本地验证：** 该转换链将 `1.000000000000000001` 变成请求字符串 `1`。这是 18 位资产可表达的输入示例；是否允许该笔下单还取决于具体资产精度、限额和余额，不宣称所有资产都接受 18 位。

**建议验收：** 输入、余额、限额、确认快照和提交金额保持十进制字符串；严格按资产精度校验；仅非权威展示可以转换；覆盖 1e-18、超过 2^53、尾随零、最大金额和手续费边界。不要通过放宽后端精度校验修补前端失真。

**依据：** `pc/src/views/Swap.vue:58`、`pc/src/api/swap.ts:46`、`pc/src/api/swap.ts:30`、`pc/src/api/backendAdapters.ts:1343`。

**范围说明：** Mobile 闪兑下单已使用 DecimalText，不能说两端提交都存在同样问题；其返回报价的金额仍转 number，展示精度可以另行核对。依据：`mobile/src/api/swap.ts:49`。

## R03 / P1：代理佣金统计、分页和冲回证据需要统一

**确认事实：**

- 佣金列表 `total_records` 是本页长度，“总佣金”是本页金额相加，还会直接混加不同发放币种。
- 接口默认上限 100 条，门户请求不传分页参数；页面没有接入服务端翻页。仅表格本地分页不能取回后续记录。
- 页面没有发放币种列，却展示佣金金额和总额。
- 原付款流水的 LEFT JOIN 限定佣金状态为 settled。变成 reversed 后，佣金行仍在，但原付款流水关联变空；代理响应没有新增冲回凭证。
- 新的扣回流水使用 `agent_commission_reversal`，Mobile 现有已知类型映射只包含 payout，没有专用冲回文案。

**业务影响：** 代理无法可靠回答“这段时间应得多少、付了多少、为什么扣回、现在净入账多少”。这是报表/解释链缺口，不等于已发现钱包重复扣款。

**建议验收：** 返回真实筛选总数和服务端分页；按币种分别列计提、待付、已付、已冲回与净入账，明确拒绝项是否包含在统计口径；原付款与冲回证据同时保留；支持来源/时间/状态筛选和专用账单文案。未知发放资产单独标记，不混为零或默认 USDT。

**依据：** `src/modules/agent/service.rs:264`、`src/modules/agent/application.rs:246`、`src/modules/agent/infrastructure.rs:731`、`web/src/api/agent.ts:469`、`web/src/agent/pages.tsx:341`、`src/modules/admin/infrastructure/agents/reversal.rs:124`、`mobile/src/core/walletLedger.ts:306`。

**排除误报：** 代理仪表盘已经按币种返回摘要并避免顶层混币相加。本项针对佣金列表与冲回证据，不是要求重做所有仪表盘。依据：`src/modules/agent/service.rs:231`。

## R04 / P1（启用地址冷静期前）：补齐用户地址登记和可用时间

**现状：** 后端有本人地址 GET/POST 登记接口及提现安全验证；启用地址冷静期后，未登记或未成熟地址会被拒绝。当前 PC/Mobile 源码未找到该接口调用，提现表单仍以填写地址为主；已有交付记录也明确未包含客户端登记页。

**业务影响：** 若后台先启用该策略，普通用户会被要求“先登记”，但客户端没有对应操作路径。默认未启用时不能说现有提现全部不可用。

**建议验收：** 两端提供登记、网络/地址选择、准确的可用时间及冷静期提示；复用已有安全校验，不重复登记刷新成熟时间。后续若要允许名单功能，另行定义撤销、再添加是否重新计时、待审核提现处理及安全通知；现有登记表没有这些完整语义。

**依据：** `src/modules/wallet/routes/withdrawal_policy.rs:32`、`src/modules/wallet/infrastructure/withdrawal_policy.rs:284`、`src/modules/wallet/infrastructure/withdrawal_policy.rs:306`、`mobile/src/views/WithdrawView.vue:251`。

## R05 / P1（启用闪兑库存保护前）：方向可用性须在展示和报价阶段同步

**现状：** 开启库存保护会在确认阶段拒绝非配置输出币种，即反向兑换；公开交易对列表只暴露 enabled 和两套限额，没有方向库存可用性。PC 转换器仍将一条配置展开为正反两个选项，报价生成用例没有该库存方向检查。

**业务影响：** 用户可以选择方向并获得报价，最后确认时才发现该方向必然不能成交。这不是缺少后端库存拦截，也不是要让两个币种共用同一份库存预算。

**建议验收：** 公开接口返回可兑换方向和明确不可用原因，客户端据此禁用入口，报价阶段也拒绝确定不支持的方向；确认阶段继续事务复查。若确需双向库存，应先设计分别按输出资产计量的账户。报价不预留库存的模式也需明确告知，不能把展示额度当成交保证。

**依据：** `src/modules/convert/inventory.rs:58`、`src/modules/convert/infrastructure.rs:235`、`src/modules/convert/application.rs:79`、`pc/src/api/backendAdapters.ts:1335`、`pc/src/api/backendAdapters.ts:2009`。

## R06 / P2：代理订单页面补到期复核与条件单触发信息

**现状：** 秒合约倒计时归零后停计时，显示待结算；它只更新本地时间，不重新读取后端终态。已有手动刷新可以获取新状态，因此不能说结算失败。另一个独立显示缺口是代理现货查询没有读取新加的 `trigger_direction` / `triggered_at`，只能看到触发价。

**建议验收：** 到期后按页面批量、有限频率读取权威状态，隐藏页面暂停，重连/切换用户取消迟到请求；只根据后端状态进入历史，不能按倒计时推断胜负。代理现货展示上涨/下跌触发方向、已触发时间与旧规则标记。

**依据：** `web/src/agent/UserPortfolioPage.tsx:181`、`web/src/agent/UserPortfolioPage.tsx:87`、`web/src/agent/UserPortfolioPage.tsx:316`、`src/modules/agent/infrastructure.rs:516`、`web/src/agent/UserPortfolioPage.tsx:167`。

## R07 / P2：异常处理期限还应接入通知和升级

**现状：** 已有负责人、期限、审计和安全重排。检查的 `financial_retry_incidents` 写入路径只保存元数据与审计；仓库 worker 未见消费该处理期限并执行超时提醒/升级的接线。不能据此断言外部告警平台完全不存在。

**建议验收：** 针对无负责人、超期、重试积压和等待资金分别定义通知；包含投递结果、去重、确认领取和升级记录，自动恢复后停止告警。通知只能提示处理，不能直接触发退款或绕过租约。对用户公开的进度与内部错误/代理信息分离。

## R08 / P2：对账从“已有分录平衡”延伸到“每笔业务是否记全”

**现状：** 当前报表已真实提供逐资产证据、钱包差异和不可变人工留档，但只检查存在的分录；它明确不核对每笔业务应有科目是否齐全。明细上限 100，虽有真实总数及截断提示，却没有全部差异的下钻分页。当前不是自动日结。

**建议验收：** 在明确启用起点之后，按业务订单/执行记录验证应有分录是否存在、币种/金额/引用是否匹配；增加漏记、重复、科目错误等差异类型，以及受权限控制的完整分页/导出。日结必须先确定时区、截止点、迟到数据和重开规则；不能用今天余额回填历史。
